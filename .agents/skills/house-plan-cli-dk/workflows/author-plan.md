# Workflow: Author a HousePlan

<required_reading>
Read `references/cli-contract.md`, `references/survey.md`, `references/authoring-contract.md`, and `references/operations.md`. For new/changed topology or openings also read `references/geometry-pitfalls.md`. Query the running CLI with `commands`, `schema`, and `apply --help` when uncertain about installed version or argument shape.
</required_reading>

<process>
1. **Choose source and output.** Work from the repo root; run `pnpm build` only when dist is missing/stale or executable sources changed, then reuse `node dist/bin.js ...` for parseable JSON. `init` refuses an existing path (exit 2, file untouched); when a plan already exists, inspect it instead of reinitializing. Keep scratch operations and drafts outside tracked project files unless the user wants them committed. Do not use unrelated `out/` artifacts.
2. **Create or inspect.** For a new plan: `node dist/bin.js init --out plan.json`; read its returned revision 0. For an existing plan: `node dist/bin.js survey --plan plan.json` and read it with `references/survey.md`. Use `report` only when an edit needs authored coordinates. Do not confuse either command's derived data with the persisted JSON.
3. **Make explicit design choices.** Translate requirements into named levels, orthogonal centerline walls (`exterior`, `interior`, or `virtual` for open-plan boundaries), room seed points strictly inside zones, accessible doors, objects (with optional `kind` for 2D symbols), exterior site elements (`site.upsert` for terraces, porches, driveways, roof eaves, columns, entry arrows) and paired stairs/voids where needed. Put an operation **array** in `ops.json` following `schema`; order level upserts before dependent entities. Start from `templates/ground-shell.json` (one room with an entry) or `templates/two-storey-stairs.json` (connecting stair run with its upper void) rather than the large reference fixture. To modify an existing plan, include only the necessary upserts and `*.remove` operations (see `templates/remove-entity.json`), not the entire previous batch.
4. **Commit the stage in one call (default).** With `ops.json` and the freshly read revision N, run `scripts/stage_commit.py --repo REPO --plan PLAN --input ops.json --expected-revision N --out packet.json` (append `--render LEVEL:OUT ...` or `--render-all DIR`, plus `--style/--format/--area-mode/--width/--visualize-out` when a user-facing render was requested). For whole-plan reflections, rotations or translations, run `node dist/bin.js transform --plan PLAN --expected-revision N --mode reflect-x|reflect-y|reflect-diagonal|rotate-90|rotate-180|rotate-270|translate [--out NEW_PLAN]` directly instead of authoring a coordinate-math script. One `stage_commit.py` invocation performs the mechanical cycle: revision preflight → `apply` (which validates transactionally and returns `survey`) → requested renders (plus `--visualize-out` fragment). Full CLI envelopes land in `packet.json` on disk; stdout is a compact summary (revision, `valid`, `areaM2`/`netAreaM2`/delta, warning codes, render paths). Exit 0 = committed and valid; exit 2 = a gate refused and nothing was committed — fix per the packet's error/hint or envelopes and re-run with the new revision. Design decisions stay in step 3: the script never authors operations.
5. **Manual fallback (per-step control or debugging).** Run the cycle by hand exactly as below: dry-run preview (`apply --dry-run`), examine `meta.diagnostics` and the proposed plan; commit once with the unchanged actual revision; read `data.plan.revision`/`meta.revision`; require `validate.data.valid === true` and inspect warnings; render per level or `--all-levels` and verify files on disk; read back persisted state with `report`/`survey`. On exit 5 (revision conflict) reread the plan and re-evaluate; never report success from a failed write and never reuse a proposal blindly. Keep this path when a step must be inspected mid-cycle or the helper is unavailable.
</process>

<success_criteria>
- No existing plan was overwritten by initialization; the accepted batch and read-back match the user's intended layout.
- Final `validate.data.valid` is true; warnings are explicitly described, not silently ignored.
- Stage cycles ran through `scripts/stage_commit.py` with the evidence `packet.json` path returned, or through the manual fallback when per-step control was needed.
- Every requested output was actually rendered and checked on disk. Invalid or incomplete drafts are reported honestly.
</success_criteria>
